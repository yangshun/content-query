# ContentQuery design comparisons

ContentQuery follows the selected contracts in [PLAN.md](./PLAN.md). These comparisons describe design choices, not performance benchmarks or a compatibility claim with another library.

ContentQuery supplies selected Zod-backed builders as `schema` from `content-query/schema`, so consumers install only ContentQuery. Builder results retain Zod's chaining methods; collection and computed validation remain open to any Standard Schema V1 provider. The `schema.input`, `schema.output`, and `schema.infer` type helpers also work across providers. Generated runtime JavaScript does not import schemas or Zod.

| Concern                          | ContentQuery choice                                                                                                                                                                                                                                           |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Astro-style collection authoring | Standard Schema validation, native Astro-compatible named loaders and context/store helpers, optional bodies, supplied HTML, and familiar `glob()`/`file()` defaults.                                                                                         |
| Configuration discovery          | Root `content-query.config.{ts,mts,cts,js,mjs,cjs}`; a string source defaults to Markdown, or an object names a format and directory. Multiple matches fail; explicit `config` paths bypass discovery.                                                        |
| Query builders                   | Object options and immutable fluent builders compile to one portable normalized plan over JavaScript data. No Drizzle or SQL engine is required.                                                                                                              |
| Related content                  | Named relationship loading returns nested selected objects. Each query supplies its target collections with `using()`, so nothing related loads implicitly. General row-producing SQL joins are deferred.                                                     |
| Projection                       | Every scope returns only what it selects, not even `id` implicitly; unselected queries fail to type-check and run. `_adjacent`/`selectAdjacent()` add selected neighbors in a sorted sibling scope. Bodies and HTML are payloads a query requests explicitly. |
| Rendering                        | Framework-independent HTML/headings instead of a framework component. Built-in processing is library-owned; generic runtime resolvers are deferred.                                                                                                           |
| Storage                          | In-memory data or generated collection indexes and lazy item payloads. SQLite can later implement the same query contract.                                                                                                                                    |
| Output layout                    | Generated runtime files and Vite declarations share `.content-query/` directly. In-memory Vite emits only types; standalone in-memory preparation writes no files.                                                                                            |
| Artifact cleanup                 | Generated watch startup prunes obsolete collection modules from previous runs after the first valid publication. Later revisions remain for that session; Next.js also cleans its previous-run runtime entries. One-shot builds prune unused artifacts.       |
| Standalone CLI                   | CAC owns command and option parsing, short aliases, and help/version output. ContentQuery validates backend choices and scalar build options. Help and version requests skip configuration and content loading.                                               |
| Bundler integration              | `content-query build` and `buildContent()` emit ordinary ESM. The Next.js adapter owns generated builds and watching; Vite adds lifecycle and client-boundary enforcement.                                                                                    |
| Module graph                     | One generated entry per collection. A route bundles and traces only the collections it imports, and relationships load only the collections passed to `using()`.                                                                                              |
| Internal organization            | Portable query plans are separate from JavaScript execution; preparation and artifact writers are separate from the deployed runtime. Stable entry points hide subsystem layout.                                                                              |
| Source lifecycle                 | Load/validate/compute during preparation; native content loaders mutate isolated stores and asynchronous watcher callbacks publish complete batches. Deployed rendering reads captured artifacts. Live source acquisition remains deferred.                   |
| Configuration recovery           | A failed reload blocks new operations until configuration, subscriptions, and content are valid. Content edits cannot revive an older configuration.                                                                                                          |
| Declared source watching         | File/glob subscriptions cover explicit inputs under project-ignored directories, honor glob exclusions, and exclude generated output.                                                                                                                         |
| Development diagnostics          | Vite uses the value codec to preserve BigInt constraints, supported value graphs, and Error cause details across runtime boundaries.                                                                                                                          |
| Site policy                      | Routes, localization fallback, navigation, public assets, and publication rules remain application-owned.                                                                                                                                                     |

Astro, Nuxt Content, Content Collections, and Drizzle informed the original API discussions. The [normative plan](./PLAN.md) retains the relevant source links and explains deliberate differences, including relationship integrity, explicit projection, portable packaging, and the distinction between compilation timing and payload loading. The [10,000-entry benchmark](../benchmarks/README.md) compares complete application stacks; its [profiling report](../benchmarks/PROFILING.md) examines ContentQuery and Void startup/build costs.

Vite production builds prepare content only for server graphs. Before bundling, they pack item payloads into lazy source modules targeting 128 KiB, while standalone artifacts retain one immutable module per payload. This avoids per-item facades in hosts with strict entry signatures. Queries without payloads avoid payload loading in both cases; a bundled `_body` or `_rendered` request can also load neighboring payloads in its module. Host output settings continue to control the final bundle. Generated publication reuses unchanged files and uses bounded parallel I/O, and Vite's watcher excludes generated output.

Large metadata indexes and payload batches are compressed when gzip/base64 saves at least ten percent; small or incompressible data retains its uncompressed representation. Metadata initializes synchronously through a portable decoder. Each lazy payload batch is imported and expanded once, while per-entry decoding retains rich-value and alias semantics. Development uses the same bounded batches and deduplicates concurrent serialization of a revision. These are packaging optimizations; source acquisition, explicit selection, and payload behavior remain the same.

Glob acquisition bounds outstanding reads to 64, retaining sorted complete snapshots and aggregated diagnostics. Single-record queries skip redundant default sorting; explicit ordering still validates sortable fields.

## Astro, Content Collections, and Velite

ContentQuery's npm distribution supports Node.js 22.12 or later. Vite 8 and Next.js 15 or 16 are optional peers for their respective integrations; standalone consumers need neither. Published Vite declarations reference Vite's public types, while the repository develops and builds with Vite+.

The Vite plugin defaults to in-memory preparation with virtual modules and bundled production output. Standalone artifact publication requires `backend: "generated"` in Vite; the CLI, standalone build API, and Next.js adapter retain generated storage by default.

The Next.js adapter distinguishes the detached telemetry helper from the application lifecycle. That helper can evaluate development configuration without preparing content or leaving a watch session alive after the application exits.

If a declared file or glob base directory is initially missing, its own metadata is also polled to recover a lost ancestor creation notification and restore native source subscriptions. This does not poll every file in a collection or change generated-output exclusions.

Checked on October 18, 2026 against [Astro content collections](https://docs.astro.build/en/guides/content-collections/) 7.x, [Content Collections](https://www.content-collections.dev/) (`@content-collections/core` 0.15.3), and [Velite](https://velite.js.org/) 0.4.0, with 1.0.0-alpha.3 in progress. Claims about other libraries come from their documentation. Direct loader compatibility is additionally exercised with the published `@ascorbic/csv-loader` 2.0.3 and Astro 7.4.0 types, including live CSV edits and a generated consumer that blocks Astro/loader imports at runtime. That loader’s declared Astro peer range remains 4/5; the fixture verifies its actual behavior against the current public contract. Entry types were rechecked on November 5, 2026 against generated Astro 7.4.0 and Content Collections 0.15.3 declarations and Velite's documentation.

Per-entry computed context includes the collection registry key, entry ID, validated data, and optional loader-defined `source` metadata inferred through `Loader<Source>`. Built-in file metadata contains project-relative paths and, for multi-record files, record keys. This optional metadata is a ContentQuery extension; unchanged Astro loaders remain supported, while Astro's store does not retain the extra field. Captured body access and cancellation remain shared resolver inputs. Content Collections' `transform` and Velite's `transform` return a whole document, so several derived fields can share one read; ContentQuery resolves each computed field separately, and `computedFields()` lets several fields share one resolver call per entry.

### Where ContentQuery is ahead

1. **Querying.** The others return arrays and leave filtering, sorting, and pagination to application code; Content Collections documents that it does not provide sorting. ContentQuery provides typed operators, deterministic ordering with ID tie-breakers, limit/offset, counts, and `paginate()` with page numbers or opaque cursors. Each page and its total come from one query, the shape Astro's `paginate()` provides for static routes, while cursors suit "load more" lists. Drizzle and Nuxt Content 3 leave page details to the application. Equality-constrained ID queries use a lazy index per collection revision for repeated detail-page lookups. Its query plan is separate from JavaScript execution, so a SQLite backend can share the contract.
2. **Relationships.** Declared forward and inverse relationships, authored ID arrays, per-scope selection, filtering, ordering, and pagination, plus preparation-time rejection of dangling or ambiguous references. Astro's `reference()` stores IDs that pages resolve one call at a time, with no inverse lookups. Content Collections joins inside `transform` against untransformed documents. Velite has no relationship model.
3. **Payload separation.** Listing queries never load bodies, HTML, or a compiler unless they request payloads, with optional projections to narrow metadata. Content Collections and Velite place compiled content in the same generated document as metadata, so importing a collection imports every body. Astro separates `render()` but still returns full entry data. Each ContentQuery collection also has its own generated entry, and relationships load only the collections passed to `using()`, so a route's bundle and serverless trace include only the collections it queries.
4. **Portable, server-only output.** Generated output is ordinary ESM that runs without Vite, sources, or `content-query.config`. The Vite plugin rejects direct and transitive client imports. Astro is framework-bound, Content Collections needs a `writer` hook to add `server-only`, and Velite emits importable JSON without a boundary.
5. **Development correctness.** Settled-write coalescing, ordered candidate updates, cancellation, atomic publication, revision-pinned operations, recovery from invalid edits, and configuration reloads that follow the config's module graph. Content Collections reruns `transform` for every document on each change. Velite lists incremental builds as roadmap work.
6. **Validation and values.** Standard Schema, shared with Content Collections, plus bundled Zod-backed builders from `content-query/schema`; Astro and Velite require Zod. devalue preserves rich values, as in Astro; Velite's JSON output stores dates as strings.
7. **Errors.** `ContentError` codes, contextual diagnostics, and grouped failures for each preparation.

`glob()`, `file()`, default IDs, `retainBody`, and `deferRender` deliberately mirror Astro and are parity rather than differentiation. Astro added `deferRender` to `glob()` in 7.1.

MDX package widgets resolve server/browser exports independently, including external server packages. Browser entries are shared, CSS follows each document's graph, and the complete manifest remains in server output. The Vite integration preserves ordinary MDX imports and recoverable development errors. Its SSR asset URLs require an absolute deployment base. The React Router example measures framework hydration overhead as part of the page transfer.

### Gaps

Ordered roughly by impact on a documentation site such as VoidPress. Each gap has a note under [future extensions](./TODO.md#future-extensions).

1. **Fixed Markdown pipeline.** [`renderMarkdown()`](../packages/content-query/src/runtime/markdown.ts) hardcodes markdown-exit options and GitHub Light/Dark Shiki themes, and accepts no plugins. Astro, `@content-collections/markdown`, and Velite all accept remark/rehype plugins, which documentation sites use for callouts, math, code block titles, and link handling. Library-owned processing is deliberate because deployed rendering cannot replay application callbacks. Eager compilation (`deferRender: false`) runs at build time, so build-only plugins or serializable options could fit that boundary.
2. **Assets and images.** Authored image and link URLs pass through unchanged, so relative images in Markdown need application handling. Astro provides `image()` and optimization. Velite's `s.image()` and `s.file()` copy, hash, and measure assets and generate blur placeholders.
3. **MDX host coverage.** Optional `@content-query/mdx` now provides local MDX, component overrides, plugins, React islands, and full React documents through Vite SSR. The single `content-query:mdx:server` facade supplies server lookups and rendering with automatic asset resolution. Generated declarations and build intermediates live under `.content-query/mdx/`, sharing the existing generated directory. Host rerenders preserve widget state until the rendered HTML changes, tracked with compact local revision keys. Core's HTML renderer is unchanged. Native Next.js MDX integration, other UI frameworks, remote MDX, formatted island slots, and streaming remain deferred. See the [architecture review](./MDX-ARCHITECTURE.md). Astro supports MDX and Markdoc component mapping; Content Collections offers `@content-collections/mdx` and bundler-compiled static imports, and Velite compiles `s.mdx()`.
4. **Cross-entry derivation.** `ComputedContext` exposes only one entry's collection, identity, validated data, source metadata, captured body, and cancellation. Previous/next links, tag counts, and sidebar order cannot be prepared and require application queries. Content Collections exposes `documents()` and `collection.documents()` in `transform`. Velite's `prepare` hook receives every collection. [TODO.md](./TODO.md) already tracks next/previous helpers and ordering files.
5. **Remaining derived fields.** ContentQuery now provides reusable reading time, word count, and excerpt definitions through `content-query/computed`, with Markdown/text/HTML inputs and typed selectors. Velite also ships `s.toc()`, `s.slug()`, and `s.unique()`. ContentQuery's rendered headings remain available only from the `_rendered` payload, not as queryable fields; queryable headings, TOC, slug, and uniqueness helpers remain future work.
6. **Persistent caching and evidence.** The preparation cache lives for one session ([`session.ts`](../packages/content-query/src/preparation/session.ts)), so every cold build repeats all work. Astro persists its data store, digests, and loader `meta` between builds; Content Collections memoizes transforms with `cache()`. Astro and Velite publish scale claims, while ContentQuery has no benchmark.
7. **Singletons.** Content Collections has `defineSingleton()` and Velite has `single: true`. ContentQuery's `file()` treats a top-level object as keyed entries, so site settings need a wrapper entry and `first()`.
8. **Remaining Astro host dependencies.** Content loaders now use the native named `load(context)`/store contract directly, with `schema`, `createSchema()`, `parseData()`, Markdown, digests, logger/config helpers, session metadata, and development watcher callbacks. No wrapper is needed. Full Astro configuration, persistent stores, integration hooks, component modules, image imports, and framework-specific deferred rendering remain separate capabilities. Unsupported rendering imports fail explicitly; compatibility is tested rather than claimed for every package.
9. **Live collections.** Astro live loaders fetch per request and return cache hints. ContentQuery defers this; see the [future notes](./TODO.md#live-collections-and-runtime-source-loading).
10. **Host and editor integration.** Content Collections ships Next.js, Remix, Solid Start, and Vinxi adapters; ContentQuery has Vite, the CLI, and a Next.js configuration wrapper with managed development watching. Astro generates JSON Schemas for data-file IntelliSense; ContentQuery does not. Entry types are not a gap: each collection entry exports a named type such as `ContentPost`, like Content Collections' and Velite's `Post`, with `typeName` for irregular plurals as in Content Collections. Because queries return only selected fields, `ContentPost<"id" | "title">` types those results, and standalone code can use `QueryData<typeof collections.posts>`.
11. **Ergonomics.** Every query is async, a relationship declaration needs five keys where Astro uses `reference("authors")`, and following a relationship also imports its target and passes it to `using()`. Those choices buy payload control, integrity, and per-route loading, but the simplest page is more verbose than `import { allPosts } from "content-collections"`.

## Query and development conventions

The fluent API starts from the collection handle with `posts.select(...fields)`, like Kysely's `selectFrom()`, and repeated `select()` calls add fields as Kysely's do. Detail lookups start with `posts.byId(id)`, like Mongoose's `findById(id).select(...)`, and await to one entry. The relational API uses `posts.findMany({ columns, with, where, orderBy })`. Drizzle's SQL order puts `select()` first because its columns are typed table objects; ContentQuery uses field strings on a generated collection handle, so editors check and complete field names immediately. It imports generated handles rather than runtime schema/table definitions. Drizzle's relational queries reach every declared relation through one `db` object; a ContentQuery handle reaches only the collections passed to `using()`, so a module never references data it does not query. Unlike Drizzle's relational queries, omitted `columns` and `with: true` do not select all fields: every scope lists the data it returns, so unrequested fields stay out of loader and client payloads. Both APIs support declared relationship predicates, fluent `has()` and relational `where: { author: ... }`, as well as the same scalar operators. Both APIs share ContentQuery's plan compiler/executor, count semantics, presence predicates, relation cardinality, and explicit payload requests. Tests compare normalized plans, selected values, generated consumers, and both runtime backends. Applications can export `queryStyle` from the config to allow only one of the two APIs.

Adjacent entries are query projections rather than stored relationships or collection-wide computed fields. Results-scope neighbors (`scope: "results"`, `.selectAdjacent(...fields)`) select explicit fields within the outer scope before pagination, or within a parent's related entries; explicit sibling options support detail pages whose outer query filters by ID. The fluent API provides equivalent field-list, callback, and object-options forms. Neighbors never include `id` implicitly.

Vite owns content publication; the host framework owns page data revalidation. `content-query:client` supplies a small update subscription that adapters can wire to their router. The Void integration preserves component state and scroll; other Vite examples use native revalidation APIs. The Next.js adapter owns a persistent watch session and publishes generated ESM and contextual error entries into Next's module graph. These boundaries avoid coupling the core to a routing framework.
