# ContentQuery design comparisons

ContentQuery follows the selected contracts in [PLAN.md](./PLAN.md). These comparisons describe design choices, not performance benchmarks or a compatibility claim with another library.

| Concern                          | ContentQuery choice                                                                                                                                                                                                                         |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Astro-style collection authoring | Standard Schema validation, native Astro-compatible named loaders and context/store helpers, optional bodies, supplied HTML, and familiar `glob()`/`file()` defaults.                                                                       |
| Configuration discovery          | Root `content-query.config.{ts,mts,cts,js,mjs,cjs}`; a string source defaults to Markdown, or an object names a format and directory. Multiple matches fail; explicit `config` paths bypass discovery.                                       |
| Query builders                   | Object options and immutable fluent builders compile to one portable normalized plan over JavaScript data. No Drizzle or SQL engine is required.                                                                                            |
| Related content                  | Named relationship loading returns nested selected objects. General row-producing SQL joins are deferred.                                                                                                                                   |
| Projection                       | Root and nested row results require explicit selection. `_adjacent`/`selectAdjacent()` add selected neighbors in a sorted sibling scope. Body/render output is separate.                                                                    |
| Rendering                        | Framework-independent HTML/headings instead of a framework component. Built-in processing is library-owned; generic runtime resolvers are deferred.                                                                                         |
| Storage                          | In-memory data or generated collection indexes and lazy item payloads. SQLite can later implement the same query contract.                                                                                                                  |
| Output layout                    | Generated runtime files and Vite declarations share `.content-query/` directly. In-memory Vite emits only types; standalone in-memory preparation writes no files.                                                                           |
| Standalone CLI                   | CAC owns command and option parsing, short aliases, and help/version output. ContentQuery validates backend choices and scalar build options. Help and version requests skip configuration and content loading.                             |
| Bundler integration              | `content-query build` and `buildContent()` emit ordinary ESM. The [Next.js example](../examples/next/README.md) uses this API; Vite adds lifecycle and client-boundary enforcement.                                                          |
| Internal organization            | Portable query plans are separate from JavaScript execution; preparation and artifact writers are separate from the deployed runtime. Stable entry points hide subsystem layout.                                                            |
| Source lifecycle                 | Load/validate/compute during preparation; native content loaders mutate isolated stores and asynchronous watcher callbacks publish complete batches. Deployed rendering reads captured artifacts. Live source acquisition remains deferred. |
| Configuration recovery           | A failed reload blocks new operations until configuration, subscriptions, and content are valid. Content edits cannot revive an older configuration.                                                                                        |
| Declared source watching         | File/glob subscriptions cover explicit inputs under project-ignored directories, honor glob exclusions, and exclude generated output.                                                                                                       |
| Development diagnostics          | Vite uses the value codec to preserve BigInt constraints, supported value graphs, and Error cause details across runtime boundaries.                                                                                                        |
| Site policy                      | Routes, localization fallback, navigation, public assets, and publication rules remain application-owned.                                                                                                                                   |

Astro, Nuxt Content, Content Collections, and Drizzle informed the original API discussions. The [normative plan](./PLAN.md) retains the relevant source links and explains deliberate differences, including relationship integrity, explicit projection, portable packaging, and the distinction between compilation timing and payload loading. No redesign benchmark has been measured.

## Astro, Content Collections, and Velite

Checked on October 18, 2026 against [Astro content collections](https://docs.astro.build/en/guides/content-collections/) 7.x, [Content Collections](https://www.content-collections.dev/) (`@content-collections/core` 0.15.3), and [Velite](https://velite.js.org/) 0.4.0, with 1.0.0-alpha.3 in progress. Claims about other libraries come from their documentation. Direct loader compatibility is additionally exercised with the published `@ascorbic/csv-loader` 2.0.3 and Astro 7.4.0 types, including live CSV edits and a generated consumer that blocks Astro/loader imports at runtime. That loader’s declared Astro peer range remains 4/5; the fixture verifies its actual behavior against the current public contract.

### Where ContentQuery is ahead

1. **Querying.** The others return arrays and leave filtering, sorting, and pagination to application code; Content Collections documents that it does not provide sorting. ContentQuery provides typed operators, deterministic ordering with ID tie-breakers, pagination, and counts. Its query plan is separate from JavaScript execution, so a SQLite backend can share the contract.
2. **Relationships.** Declared forward and inverse relationships, authored ID arrays, per-scope selection, filtering, ordering, and pagination, plus preparation-time rejection of dangling or ambiguous references. Astro's `reference()` stores IDs that pages resolve one call at a time, with no inverse lookups. Content Collections joins inside `transform` against untransformed documents. Velite has no relationship model.
3. **Payload separation.** Listing queries never load bodies, HTML, or a compiler, and projection is mandatory. Content Collections and Velite place compiled content in the same generated document as metadata, so importing a collection imports every body. Astro separates `render()` but still returns full entry data.
4. **Portable, server-only output.** Generated output is ordinary ESM that runs without Vite, sources, or `content-query.config`. The Vite plugin rejects direct and transitive client imports. Astro is framework-bound, Content Collections needs a `writer` hook to add `server-only`, and Velite emits importable JSON without a boundary.
5. **Development correctness.** Settled-write coalescing, ordered candidate updates, cancellation, atomic publication, revision-pinned operations, recovery from invalid edits, and configuration reloads that follow the config's module graph. Content Collections reruns `transform` for every document on each change. Velite lists incremental builds as roadmap work.
6. **Validation and values.** Standard Schema, shared with Content Collections; Astro and Velite require Zod. devalue preserves rich values, as in Astro; Velite's JSON output stores dates as strings.
7. **Errors.** `ContentError` codes, contextual diagnostics, and grouped failures for each preparation.

`glob()`, `file()`, default IDs, `retainBody`, and `deferRender` deliberately mirror Astro and are parity rather than differentiation. Astro added `deferRender` to `glob()` in 7.1.

### Gaps

Ordered roughly by impact on a documentation site such as VoidPress. Each gap has a note under [future extensions](./PLAN.md#future-extensions).

1. **Fixed Markdown pipeline.** [`renderMarkdown()`](../packages/content-query/src/runtime/markdown.ts) hardcodes markdown-exit options and GitHub Light/Dark Shiki themes, and accepts no plugins. Astro, `@content-collections/markdown`, and Velite all accept remark/rehype plugins, which documentation sites use for callouts, math, code block titles, and link handling. Library-owned processing is deliberate because deployed rendering cannot replay application callbacks. Eager compilation (`deferRender: false`) runs at build time, so build-only plugins or serializable options could fit that boundary.
2. **Assets and images.** Authored image and link URLs pass through unchanged, so relative images in Markdown need application handling. Astro provides `image()` and optimization. Velite's `s.image()` and `s.file()` copy, hash, and measure assets and generate blur placeholders.
3. **MDX and components.** Output is HTML only. Astro supports MDX and Markdoc component mapping. Content Collections offers `@content-collections/mdx` and bundler-compiled static imports through `createDefaultImport()`. Velite compiles `s.mdx()`.
4. **Cross-entry derivation.** `ComputedContext` exposes only one entry's `id`, `data`, and `readBody()`. Previous/next links, tag counts, and sidebar order cannot be prepared and require application queries. Content Collections exposes `documents()` and `collection.documents()` in `transform`. Velite's `prepare` hook receives every collection. [TODO.md](./TODO.md) already tracks next/previous helpers and ordering files.
5. **Built-in derived fields.** Velite ships `s.toc()`, `s.excerpt()`, `s.metadata()` (reading time and word count), `s.slug()`, and `s.unique()`. ContentQuery computed fields can implement these, but none are provided, and rendered headings are only available from `render()`, not from queries.
6. **Persistent caching and evidence.** The preparation cache lives for one session ([`session.ts`](../packages/content-query/src/preparation/session.ts)), so every cold build repeats all work. Astro persists its data store, digests, and loader `meta` between builds; Content Collections memoizes transforms with `cache()`. Astro and Velite publish scale claims, while ContentQuery has no benchmark.
7. **Singletons.** Content Collections has `defineSingleton()` and Velite has `single: true`. ContentQuery's `file()` treats a top-level object as keyed entries, so site settings need a wrapper entry and `first()`.
8. **Remaining Astro host dependencies.** Content loaders now use the native named `load(context)`/store contract directly, with `schema`, `createSchema()`, `parseData()`, Markdown, digests, logger/config helpers, session metadata, and development watcher callbacks. No wrapper is needed. Full Astro configuration, persistent stores, integration hooks, component modules, image imports, and framework-specific deferred rendering remain separate capabilities. Unsupported rendering imports fail explicitly; compatibility is tested rather than claimed for every package.
9. **Live collections.** Astro live loaders fetch per request and return cache hints. ContentQuery defers this; see the [future notes](./PLAN.md#live-collections-and-runtime-source-loading).
10. **Host and editor integration.** Content Collections ships Next.js, Remix, Solid Start, and Vinxi adapters; ContentQuery has Vite and the CLI, with Next.js outside v1. Astro generates JSON Schemas for data-file IntelliSense. ContentQuery exposes entry types only through `QueryData<typeof collections.posts>`.
11. **Ergonomics.** Every query is async and must select fields, and a relationship declaration needs five keys where Astro uses `reference("authors")`. Those choices buy payload control and integrity, but the simplest page is more verbose than `import { allPosts } from "content-collections"`.

## Query and development conventions

The object API uses familiar `where`, `select`, and `orderBy` options without adopting Prisma's database or code generator. It shares ContentQuery's fluent plan compiler/executor, count semantics, presence predicates, relation cardinality, and explicit body/render operations. Tests compare normalized plans, selected values, generated consumers, and both runtime backends.

Adjacent entries are query projections rather than stored relationships or collection-wide computed fields. Shorthand selects neighbor IDs in the outer scope before pagination; explicit sibling options support detail pages whose outer query filters by ID. The fluent API provides equivalent shorthand, callback, and object-options forms.

Vite owns content publication; the host framework owns page data revalidation. `content-query:client` supplies a small update subscription that adapters can wire to their router. The Void integration preserves component state and scroll; other Vite examples use native revalidation APIs. The standalone Next.js example requires a restart after content edits. These boundaries avoid coupling the core to a routing framework.
